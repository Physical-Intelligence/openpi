# 遥操作数采操作手册

本文是 UR5 双轴腕实验的中文项目文档，不是 Physical Intelligence 官方 OpenPI 原文。

本文只讲最小闭环的前半段：

```text
SpaceMouse
→ UR5 + 双轴腕 + 夹爪
→ 三台 RealSense D435
→ 10 Hz 原始 HDF5
→ 数据验证
```

键位、轴方向和零位请同时阅读[遥操作键位与零位](02_遥操作键位与零位.md)，
9 维 state/action 请阅读[动作空间与数据格式](05_动作空间与数据格式.md)。

线程所有权和 fail-closed 行为。

但“真实软件路径已接线”和“已完成现场验收”不是一回事。当前
`teleop_collect.py` 的 dry-run、`--fake` 和四道门禁后的真实路径都只使用本项目代码，
不导入或运行 `/home/user/shiyi/slai-manipulation`。`teleop_hardware.py` 的单
actuator-owner、`teleop_session.py` 的 125 Hz SpaceMouse keepalive/按键生命周期、
独立 10 Hz recorder 线程和 `teleop_collect.py::_run_real_collection` 已完成软件接线，
且有可注入 Fake 测试。当前安全限位与旧采集进程仍会让 preflight 拒绝真实运行，
这条路径也尚未连接真机。因此本手册不宣称真机遥操数采已验证。

## 安全规则

1. 默认命令只能只读、Fake、dry-run 或 shadow。
2. 真实运动必须同时提供 `--enable-motion` 和精确确认字符串。
3. UR 急停、PolyScope 安全设置永远高于 Python 软件。
4. `safety.yaml` 中未知的现场 joint limits 必须保持 `null`，让 real-ready 检查失败；不要猜数值填入。
5. NaN/Inf、状态过期、相机超时/skew、串口异常、重复帧或控制语义不一致时，当前 episode 必须拒收。
6. 录制时禁止使用会产生 `speedJ` 的 J6 jog；训练 action 的前六维只能保持 `speedL` 语义。
7. 相机按 serial 绑定 `front/side/top`，不能按 `/dev/video*` 或枚举顺序判断角色。

## 主从腕启动和 Ctrl 接管语义

遥操数采的默认手腕路径是 ESP32 主腕→OpenRB 从腕，而不是长期由 SpaceMouse 控制手腕。
统一 hardware owner 应按下列顺序管理它：

```python
config = load_project_config(config_dir)
wrist = WristMasterSlaveController(config)
wrist.connect(enable_motion=True)  # 会执行从腕 HOME，结束后 parked
wrist.resume_master()              # 当前主腕姿态设为相对零

# 由同一 hardware owner 线程以 50 Hz 调用
state = wrist.step()

# 录制器/UI 只读不发串口 I/O 的缓存
cached = wrist.get()
```

`connect(enable_motion=True)` 内含“直接回 YAML servo_zero_raw”，是真实运动。没有
`--enable-motion` 时统一入口不得调用它。如果只需读 OpenRB 当前状态，可由诊断工具单独使用
`OpenRBWrist.connect(); get()`；
这个只读路径不等于已启动主从跟随。

跟随期间按住 Ctrl 时，SpaceMouse J1/J2 速度覆盖主腕目标，UR twist 必须清零。
底层 controller 单独 clear 时只会清速并保持目标；完整的 `TeleopHardwareWorker`
会在 Ctrl 松开边沿先 clear，再以松开时主腕姿态调用 `resume_master()`，安全重建
相对零并自动恢复 ESP32 主腕跟随。非 override 状态下不会在每个周期重复建零。

任意主腕 TELE 超时/重复/倒退、`zero_valid=0`、OpenRB 故障/状态过期或串口异常都必须
触发统一 stop，不得在数采线程中捕获后忽略。

2026-08-31 最新只读预检已确认：3/3 台配置相机、3 个 `/dev/serial/by-id/` 节点、

1. PolyScope `joint_min_rad/joint_max_rad` 仍为 `null`。
2. PID 1476 的 `slai_mi.ui.collection_frontend --spacemouse-collection-launch` 仍在运行。


安全配置、进程互斥和 preflight 全部通过后，首条数据仍只做低速、小范围、
短 episode。当前软件定义的流程为：

1. 启动时保持 SpaceMouse 帽居中，主腕保持自然姿态，等待协调 Home。
2. worker 内部的腕 `connect(enable_motion=True)` 先完成从腕动态 Home 并进入 parked，
   紧接着在同一 owner 线程显式 `resume_master()`，然后才对会话报告就绪。
3. 空闲时按 Menu：夹爪目标先设为 0，再执行从腕 Home + UR task-home，确认
   稳定后 `resume_master()`，等到首个完整零 `speedL` receipt 后立即开始 episode。
4. episode 已立即开始，按任务操作。
5. `Fit`：先原子封存任务数据，再在 episode 外执行完整 Home。
6. 等待 HDF5 flush/fsync 和原子重命名完成。
7. 出现异常、按 `Esc` 或未提交退出时，只接受 `rejected/` 结果，不能手改 `success=true`。

录制窗口内不要按 `1/2` 或 `T`。这些操作会产生 `speedJ`，与 9 维 action 前六维的 `speedL`
语义不同，整段数据必须拒收。

## Episode 生命周期

```text
Menu 完整 Home/resume 后的首个合格 receipt + observation
→ episode_XXXX.tmp.hdf5
→ 持续通过状态/action/相机/时间戳门禁
→ Fit 上升沿封存，Home 帧不再写入
→ flush + fsync
→ 原子改名 episode_XXXX.hdf5

任一异常、主动丢弃或进程中断
→ rejected/episode_XXXX.hdf5
```

同一输出目录有非阻塞 writer lock，只能由一个采集进程写入。硬中断留下的 `.tmp.hdf5` 会在
下次启动时移动到 `rejected/`，不会静默删除或覆盖。

未压缩的三路 `640×480×3` RGB、10 Hz 数据约为 27.6 MB/s，即约 1.66 GB/min。正式采集前应
计算任务时长、episode 数量并检查磁盘余量。
