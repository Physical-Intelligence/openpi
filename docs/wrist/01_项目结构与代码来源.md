# 项目结构与代码来源

本文是 UR5 双轴腕实验的中文项目文档，不是 Physical Intelligence 官方 OpenPI 原文。

## “旧参考工程”是什么

此前文档里的 `legacy` 只是“旧工程/历史实现”的英文简称，具体指：

```text
/home/user/shiyi/slai-manipulation
```

它不是一个机器人库，也不是 π0.5 的特殊概念。这个旧工程中有过 UR5、SpaceMouse、双轴腕、
两种夹爪和三相机同步的真机实现，所以它是很有价值的**只读历史参考**。“历史实现
曾工作”不等于“当前项目的新驱动已完成真机验收”。

当前默认运行路径不导入 `slai_mi`，不启动旧虚拟环境，也不需要把
`/home/user/shiyi/slai-manipulation` 加入 `PYTHONPATH`。`legacy_adapter.py` 和
`legacy_collection_adapter.py` 是早期迁移留下的隔离适配文件，不在新
`teleop_collect.py` 的默认 import/运行链上。未经明确回滚决定，不应再调用它们。

提取原则是：

1. 只提取与本实验相关、已经验证过的逻辑。
2. 不复制旧工程里的 OpenPI、训练代码或虚拟环境。
3. 所有新硬件模块导入时不连接设备。
4. 真实运动仍必须经过显式门禁。
5. 本地模块先通过 Fake 和只读测试；未经低速真机验收前不宣称已替代历史实现。

## 运行时分层

下面是本项目当前的本地分层。底层控制器、三相机、`teleop_hardware.py`
和 `teleop_session.py` 已组成 `teleop_collect.py` 真实入口，并用可注入 Fake
验证了软件时序。这只能称为“软件接线完成”；当前 preflight
仍被安全限位和旧进程占用门禁阻止，也没有做真机低速验收。

```text
SpaceMouse 输入
  → teleop_session.py 的 125 Hz keepalive/按键生命周期
  → teleop.yaml 轴/键位映射
  → teleop_hardware.py 单 actuator-owner 与 safety filter
  → UR5 / 双轴腕 / 夹爪控制器
  → 控制周期完成后的 command receipt

三台 D435 独立采集线程
  → 按 serial 绑定 front/side/top
  → 最近帧同步和 skew/timeout 门禁

设备状态 + 三路图像 + command receipt
  → teleop_session.py 中独立的 10 Hz HDF5 recorder 线程
  → 成功原子 rename / 异常进入 rejected
```

上述默认链路的 import 闭包在当前 `openpi` 工作树中，不依赖旧工程运行时。

## Python 依赖为什么不只是 pyserial

- 手腕、幻尔夹爪、飞特夹爪：`pyserial==3.5`。
- UR5：`ur-rtde==1.6.3`，提供 `rtde_control` 和 `rtde_receive`。
- D435：`pyrealsense2==2.56.5.9235`。
- SpaceMouse：项目内 ctypes wrapper + 系统 `libspnav`，同时需要 `spacenavd` 服务。

这三个 Python 包被放在 `hardware` 依赖组，版本来自已工作环境。4090 使用：

```bash
uv sync --group hardware
```

H100 训练机不需要安装硬件组，但仍使用完全相同的 `pyproject.toml` 和 `uv.lock`。

## 代码来源追踪

项目内硬件控制模块的行为参考旧工程以下文件：

- UR：`src/slai_mi/devices/ur5/`。
- SpaceMouse：`src/slai_mi/devices/spacemouse/` 和 `site_adapter.py`。
- 双轴腕：`src/slai_mi/devices/wrist_sensor/`。
- 夹爪：`src/slai_mi/devices/gripper/`。
- 相机：`src/slai_mi/devices/cameras/realsense_capture.py`。

旧工程保持不动，只用于审计协议、参数和既有行为。当前项目默认运行已不依赖它；
新的真实遥操 episode 入口已完成项目内软件接线，但仍必须完成低速验收和
安全故障注入，才能宣布整条数采链已真机验证。
